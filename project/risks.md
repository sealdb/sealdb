> 每个风险必须有：触发信号、缓解措施、负责人/阶段。  
> 风险状态在 `progress.md`/本文件更新；关闭时写“如何验证已解除”。

## 2. 风险处理原则

1. **先消除“不可构建/不可复现”风险**（R8/R14/R13），再谈功能。
2. **每个阶段只允许 1–2 个高风险项**；超出则缩范围，不加人硬堆。
3. **风险触发即记录**：在 `progress.md` 当日条目写“触发 Rxx”，不要事后补。
4. **缓解措施必须有验证方式**：例如“固定 8.5.x”要能在 CI 配置中看到。

## 4. 假设（Assumptions）

| ID | 假设 | 若不成立的影响 |
|---|---|---|
| A1 | TiDB v8.5.8 是行为基准 | 需重新冻结语料/计划 |
| A2 | PD/TiKV 协议与 8.5 兼容 | 客户端/测试需调整 |
| A3 | 可以运行 Go 工具链构建 Oracle | 需改用预生成金样 |
| A4 | 测试环境可运行 docker（PD+TiKV） | 集成测试降级为 mock |
| A5 | 允许使用 `tikv-client` 0.4.x | 需自研 gRPC 客户端 |
| A6 | 首版不需要 TiFlash/MPP | 否则范围显著扩大 |
| A7 | 团队可接受较长周期（数月到数年） | 需缩小目标/增加人力 |

## 5. 风险评审节奏

- **每周**：更新高风险项状态；检查是否有新触发。
- **每阶段 Gate**：逐项确认缓解是否有效；未关闭的高风险不得进入下一阶段（除非用户接受）。
- **每季度**：重新评估 R1（规模）与 R5（行为细节），决定是否调整范围。
